# Антон: схема серверной версии

## Короткий ответ

Браузерный сайт не должен подключаться к PostgreSQL напрямую. Между ними нужен серверный API:

```text
Врач / пациент
      │ HTTPS
      ▼
Сайт (интерфейс) ── HTTPS ──► API Антона ── закрытая сеть ──► PostgreSQL
                                     │
                                     ├── приватное хранилище файлов
                                     └── журнал аудита
```

Текущая демоверсия в `dist/` — статический сайт: записи существуют только в памяти вкладки и сбрасываются после обновления. GitHub Pages годится для показа только синтетических данных. Вводить реальные сведения пациентов в эту версию нельзя.

## Где хранить

1. **PostgreSQL** в управляемой инфраструктуре медицинской организации или российского провайдера после проверки его условий и требований к данным. В БД хранить учётные записи и учреждения, карточку пациента, заявку, коды, предложения, этапы, согласия и метаданные вложений.
2. **Приватное объектное хранилище** для файлов анализов. Бакет закрытый; публичные URL выключены. API после проверки прав выдаёт короткоживущую ссылку на скачивание. В PostgreSQL хранить случайный ключ объекта, тип и размер файла, контрольную сумму и результат антивирусной проверки — не содержимое документа.
3. **Резервные копии** зашифрованно на отдельной площадке с ограниченным доступом. Настроить сроки хранения и регулярно проверять восстановление.

Не хранить пациентские данные в Git, GitHub Pages, JavaScript, `localStorage`, публичных папках, таблицах общего доступа или резервных копиях без шифрования. Не открывать порт PostgreSQL в интернет.

## Минимальная модель данных

```text
users                 учётные записи врачей и администраторов
organizations         амбулатории и стационары
user_organizations    членство пользователя в организации и его роль
patients              минимальные идентификационные сведения пациента
referrals             заявка, диагноз, операция, оплата и текущий статус
referral_offers       предложения стационаров, дата, условия и исход
clinic_capacity       профиль, плановые слоты и доступность учреждения
attachments           метаданные приватных файлов
consents              основание, текст/версия и дата согласия или уведомления
audit_events          кто, когда и что сделал с заявкой
```

Каждая заявка получает случайный внутренний UUID. Не использовать номер полиса или СНИЛС как ID в URL. СНИЛС собирать только если его необходимость подтверждена владельцем процесса и специалистами по защите данных; по возможности оставлять только идентификатор, реально требуемый согласованным сценарием. Для поиска по полису сохранять шифротекст и отдельный HMAC-индекс для точного сопоставления; обычный хеш номера недостаточен, так как пространство номеров ограничено.

Пример существенных полей (не готовая миграция):

```sql
CREATE TABLE referrals (
  id uuid PRIMARY KEY,
  patient_id uuid NOT NULL REFERENCES patients(id),
  created_by uuid NOT NULL REFERENCES users(id),
  source_organization_id uuid NOT NULL REFERENCES organizations(id),
  status text NOT NULL,
  diagnosis_text text NOT NULL,
  icd10_code text,
  procedure_text text NOT NULL,
  procedure_code text,
  payment_type text NOT NULL,
  requires_in_person_exam boolean NOT NULL DEFAULT false,
  comment text,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  version integer NOT NULL DEFAULT 1
);
```

Коды МКБ и операций лучше ссылать на версионируемые справочники, а не хранить только подпись из выпадающего списка. `requires_in_person_exam` — обычный маркер для врача стационара; он не должен сам менять статус или подбирать клинику.

## Как сайт связан с БД

1. Врач входит на сайт; сервер создаёт защищённую сессию. В браузере — cookie `HttpOnly`, `Secure`, `SameSite`; для врачей включить многофакторный вход, где это возможно.
2. Сайт посылает запросы на тот же домен, например `GET /api/referrals?scope=mine` или `POST /api/referrals`.
3. API получает пользователя из сессии, проверяет роль, его медицинскую организацию и доступ к конкретной заявке. Амбулаторный врач получает только собственные заявки; стационарный — только согласованную область заявок стационара; администратор — административные полномочия. Проверки выполняются на сервере для каждого запроса.
4. API валидирует поля и допустимый переход статуса, затем обращается к БД через серверный драйвер PostgreSQL и параметризованные SQL-запросы.
5. Изменение статуса, предложение, просмотр чувствительной карточки и доступ к файлу записываются в аудит. Журнал должен быть защищён от редактирования обычными пользователями.

Пример кода сайта:

```js
const response = await fetch('/api/referrals?scope=mine', {
  credentials: 'include',
  headers: { Accept: 'application/json' }
});
if (!response.ok) throw new Error('Не удалось загрузить заявки');
const referrals = await response.json();
```

Пример соединения **на сервере API** (не в `dist/app.js`):

```js
import pg from 'pg';
const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });

const result = await pool.query(
  'SELECT id, status, procedure_text FROM referrals WHERE created_by = $1 ORDER BY created_at DESC',
  [authenticatedUser.id]
);
```

`DATABASE_URL` задаётся в защищённой конфигурации сервера/хранилище секретов. Сервисный пользователь БД получает только необходимые права. Значение URL подключения, пароль и ключи шифрования никогда не публикуются в HTML, браузерном JavaScript, Git или журнале ошибок.

## Набор API для первого этапа

```text
POST   /api/session                  вход врача
DELETE /api/session                  выход
GET    /api/referrals?scope=mine     заявки текущего врача
POST   /api/referrals                создать черновик/заявку
GET    /api/referrals/:id            карточка с проверкой доступа
PATCH  /api/referrals/:id            исправить разрешённые поля
POST   /api/referrals/:id/offers     создать предложение стационара
POST   /api/referrals/:id/status     допустимый переход статуса + основание
POST   /api/referrals/:id/files      безопасная загрузка файла
GET    /api/referrals/:id/files/:fileId  выдать файл после проверки прав
GET    /api/patient/status           отдельный пациентский сценарий после проверки личности
```

Не принимать роль, автора, организацию или итоговые права из полей запроса как доверенные значения: их сервер определяет из сессии. Для запросов изменения использовать защиту от CSRF, ограничения размера и типа файлов, проверку содержимого, журналирование и ограничение частоты запросов.

## Развёртывание

Для пилота: домен и TLS → reverse proxy → сервер приложения/API → PostgreSQL и приватное файловое хранилище в закрытой сети. Статические файлы сайта можно отдавать тем же доменом, что упрощает настройку сессии. Если сайт отдельно на GitHub Pages, он должен оставаться только интерфейсом для синтетического демо; рабочие пациентские данные должны идти через утверждённый защищённый контур, а не из публичного хостинга.

Перед вводом реальных данных определить с медицинской организацией роли и область видимости, цель и состав собираемых сведений, сроки хранения и удаления, основания доступа и обмена, модель угроз, порядок реагирования на инцидент, договоры с поставщиками инфраструктуры, резервирование и тест восстановления. Это отдельный этап проектирования и согласования, а не настройка одной базы данных.

## Этапы перехода с демо

1. С врачами утвердить поля, статусы, роли, доступность мест и процесс согласования ОМС/платно.
2. Утвердить архитектуру, хостинг, модель доступа, аудит, правила хранения файлов и резервирования.
3. Поднять API и тестовую PostgreSQL с вымышленными данными; покрыть ролевые проверки тестами.
4. Подключить интерфейс к тестовому API и проверить сценарии врачей и пациента.
5. Провести проверку безопасности и согласования организации до любого ввода данных реальных пациентов.
